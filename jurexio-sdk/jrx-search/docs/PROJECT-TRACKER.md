## 1. Ecosystem architecture (always keep in mind)

NYS Knowledgesearch is **not a standalone product** — it is the legal-intelligence layer of the Nyayavigya Platform:

```
Nyayasiddhi platforms (NSP · NYM · NYS-INS · NYS-ACE · NYS-MIN · Jurexio)
        │
        ▼
Nyayavigya Agentic AI SDK  — orchestration · agents · patterns · RAG · memory · CoT
        │   ALL legal intelligence & legal tasks (any jurisdiction, US + IN first)
        │   flow through this platform via MCP tools + typed SDK
        ▼
NYS KNOWLEDGESEARCH  (this project — same NYV AWS infrastructure & namespace;
                      will adopt the shared NYV dashboard once developed)
        │
CourtListener (US) · RDS full IN corpus · NCRB Sankalan statutes · owned S3 PDF buckets
```

Standing architectural rules:
1. **Nyayasiddhi brand guidelines** apply to all UI/UX and naming.
2. **AI provider policy:** Claude (Anthropic) is preferred; when Claude is unavailable (dev proxy down, Bedrock Claude not yet approved), **use the available Bedrock models** (Nova Pro for generation, Titan v2 for embeddings). Never fail an LLM task solely because Claude is unreachable.
3. **OpenAPI contract-first**, additive-only; SDK and MCP tool schemas derive from the spec (no drift).
4. **No mocks, no fabricated legal text**, explicit typed errors, labeled fallbacks.
5. **Global-standards, scalable code**: stateless API, connection-pooled RDS, indexed access paths only, statement timeouts, resumable batch jobs.
6. **NYV SDK merge readiness** (see `docs/NYS-Nyayavigya-SDK-Integration-Plan-v5.md`): every new endpoint takes an explicit `jurisdiction` filter, no new LLM call sites without an injectable provider seam (NV-LLM-001), deterministic-first tools, fail loud with source metadata, additive-only contract, MCP tool names follow the NYV registry taxonomy. Post-100%, NYS merges into the Nyayavigya SDK as its knowledge plane (RAG tier + executable MCP handlers + citation-verification oracle) per phases M0–M4 in the plan.

- Hybrid retrieval: FTS ∪ pgvector with Reciprocal Rank Fusion; cross-encoder reranking; query expansion + jurisdiction/court/section detection before retrieval.
- Passage-level retrieval over full judgment text (PDF extraction plane) — not just metadata.
- Citation-graph signals (treatment, depth) in ranking; parenthetical-style distilled snippets.
- Retrieval benchmark suite (BigLaw-Bench-Retrieval style: long judgments, cross-references) run in CI; every retriever change must hold or improve scores.
- Rubric benchmark scorecard published per release (Harvey Legal Agent Benchmark methodology — our 144-task judge is the harness).

### 6.2 Scale: 10K users at launch → 1M
| Stage | Targets | Levers |
|---|---|---|
| 10K users (initial prod) | p95 search < 500ms, run start < 2s, zero silent errors | RDS parameter tuning (work_mem), HNSW params, connection pool sizing, API-level caching of hot statutes/templates, load test (k6) before launch |
| 100K | Horizontal API | Stateless API behind ALB (already), read replica for search traffic, Redis/semantic cache layer, rate limiting + API-key metering |
| 1M | Full NYV-scale | Job-queue execution for runs (no 90s synchronous HTTP), CDN static, partitioned/sharded corpus indexes, dedicated embedding service, observability (CloudWatch dashboards, SLOs), chaos/regression drills |

Each stage gates on a load-test report + the §4 ship gate.
